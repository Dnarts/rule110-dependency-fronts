# Прошлый выбор и однобитная обратная связь в OLMo

Контракт второй серии, редакция после проверки пяти лакун. Единица проверки — один фиксированный текстовый интерфейс одного замороженного чекпойнта. Отдельные строки, переиспользующие один префикс, не являются независимыми экземплярами модели. Здесь заданы правила вынесения вердикта. Результаты первой серии хранятся в `gates-02.json`.

## 1. Что должен вычислять получатель

Пусть собственный выбор модели равен $h=0$ для A и $h=1$ для B. Скрытое правильное правило — $p$. Наблюдатель возвращает $e=h\oplus p$, где 1 означает ошибку. Для каждого полученного выбора испытываем оба скрытых мира. Новая строка имеет вид $x=L\,u\,R$, где $u$ — середина, а $L,R$ — независимые биты. Правильный выход равен

$$
p=h\oplus e,\qquad y=f_p(x)=\begin{cases}L,&p=0,\\R,&p=1.\end{cases}
$$

При $L\ne R$ получается $y=L\oplus h\oplus e$. Первый протокол допускал только такие строки. Получатель, полностью игнорирующий последний бит, может набрать 100%. При $L=R$ правильный выход равен $L$ для всех $h,e$. Для проверки выбора конца нужны все четыре сочетания концов при одной середине.

Если полный доступный вход после стирания выбора одинаков для A и B при фиксированных $e,x$, детерминированный бинарный ответ при $L\ne R$ верен ровно в одной из двух историй. Точность по строкам равна 50%, число полностью решённых пар равно нулю. При воздержаниях 50% — верхняя граница. При $L=R$ точность может равняться 100%. На равномерной смеси всех четырёх сочетаний концов верхняя граница точности без $h$ равна 75%. Для декодера без $e$ границы по отдельным ответам те же при балансе скрытых миров. В таблицах всегда указываются условие и знаменатель.

## 2. Панель и счёт

Для новой панели взять все 64 шестибитные середины в порядке возрастания SHA-256 от ASCII-строки `observer-v2|` с дописанной серединой, включая ведущие нули. Позиции 1–8 образуют dev, 9–20 — общий замороженный тест G1 и G2, 21–32 — тест G3, 33–44 — тест G4. Позиции 45–64 остаются в резерве. Все строки восьмибитные. Для каждой середины предъявить полное произведение $(L,R,h,e)\in\{0,1\}^4$. Это 16 условий с одинаковой серединой. Демонстрации используют другие строки. Для каждого префикса обрабатывать середины в порядке хеша, внутри середины — лексикографический порядок (L,R,h,e) с 0 перед 1. Каждая ветвь стартует с изолированного снимка. Отбор формулировки, числа демонстраций, слоя или вектора возможен на dev. До открытия отложенной панели замораживаются все сравниваемые условия. Новый метод, выбранный после её открытия, требует свежей панели.

**Получение собственного выбора.** Для одного префикса вычислить на температуре 1 обе вероятности A/B с нормировкой по полному словарю. Требовать $P(A)\ge0.01$ и $P(B)\ge0.01$. Использовать закреплённые в исходном скорере 1024 выборки с возвращением, генератор Python Random с seed 110 и порог $q_A=P(A)/(P(A)+P(B))$ на равномерном числе. Сохранить все выборы, исходные вероятности и индексы первых A и B. Для каждой истории взять её первое фактическое появление, провести выбранный токен через модель и лишь затем снять кэш. При недостижении любого минимума или отсутствии хотя бы одной буквы в 1024 попытках статус префикса NOT_EVALUABLE. Повторные выборки и принудительное дописывание буквы в эту попытку не входят. Вероятностные пороги — принятые для протокола рабочие значения.

**Формат ответа.** Для каждой обязательной строки с числовым ответом G1–G4, включая патчи, нейтральные контроли и измерения после возврата, вычислить $P(0),P(1)$ через logsumexp по полному словарю в FP32 или выше. Сохранить их сумму $q$, зазор $m=\ell_1-\ell_0$, полнословарный greedy и целевой бит. Условие PASS для формата — конечные значения и $q\ge0.80$ на **каждой** такой строке. Минимум берётся до любого отбора удачных блоков. Одна конечная масса ниже порога даёт FAIL_FORMAT для этого гейта даже при верном знаке всех зазоров. Строки остаются в знаменателе и в отчёте. Нулевой зазор — воздержание и неуспех строки. При $q\ge0.80$ победитель среди двух битов получает как минимум 0.40, а любой другой токен — не более 0.20. При строгом знаке зазора выбранный бит тем самым является и полнословарным greedy. Порог абсолютный, сравнения со средним по текстовой панели для допуска нет. Буквенные диагностические запросы логируются отдельно.

**Техническое равенство.** G0, G0R и последующие контроли копирования используют одну раскладку входа и один способ исполнения. Сначала проверить форму, исходный dtype, конечность всех элементов и сравнить байты в логическом порядке в исходной точности. Для полных логитов дополнительно потребовать max_abs_diff == 0.0, вычисляя разность после точного расширения BF16/FP16 до FP32. Допуск равен нулю. Например, разные знаки машинного нуля численно равны, но нарушают побайтовое условие. Для кэша сравнить все активные K/V по слоям и токенам, offsets, порядок видимых позиций, индексы кольцевых буферов и соответствие позициям RoPE. Свободная ёмкость буфера вне видимого диапазона в сравнение не входит. Несовпадение в обязательном техническом контроле, неверная граница токенов либо NaN/Inf дают INVALID.

Основная поведенческая единица — середина, на которой верны **все 16** ответов. Предлагаемый порог ≥75% составляет 6/8 полных блоков на dev и 9/12 на отложенной панели. Это операционный порог на фиксированной панели. Для утверждения о точном декодере на всей испытанной конечной области нужны все блоки. Дополнительно приводятся оба старых счётчика пар по $e$, сырые зазоры и ошибки на каждом из четырёх сочетаний концов.

## 3. Гейты

**G0 — идентичность и изоляция.** Проверить веса, токенизатор, однотокеновые A/B/X, выходные 0/1 в контексте, точные ID суффикса, формы, dtype и позиции RoPE. В G0 входят снимки $C_A,C_B$ после выбора. Все диагностические и основные запросы исполняются на новых копиях соответствующего снимка. До и после диагностики сверяются байты активных K/V каждого слоя, offset, положение в кольцевом буфере и остальные метаданные, определяющие видимые позиции. На одном и том же основном запросе сравнить полные логиты при выполнении с пропущенной диагностикой и после диагностики. PASS требует точного совпадения всего этого для A и B. Измерение логитов recall заканчивается до подачи предсказанной буквы обратно.

**G0R — обратимость до поведенческого отбора.** До открытия отложенной панели для каждого выбранного префикса, каждой dev-строки и обоих текстовых сигналов сравнить натуральные ветви с цепочкой `C_A → P_B(C_A) → P_A(P_B(C_A))` и зеркальной цепочкой из B. Снимки делаются до $e$. $P_h$ переписывает только K/V одной позиции выбора во всех слоях из независимого эталона $C_h$. Обратный патч применяется к результату первого. Для чтения полных логитов каждой точки подаётся тот же суффикс на одноразовой копии этой точки. В середине требуются равенство активного кэша, метаданных и логитов с натуральным донором. В конце все три величины должны совпасть с исходной историей. Эталоны сохраняют свои исходные отпечатки. PASS требует точного совпадения во всех проверках, независимо от того, какую цифру предпочитает модель. Для первого G0R на Base использовать ровно общий префикс prefix(8) из observer_gates.py, панель dev и два направления подмены. До первой записи подтвердить побайтную идентичность всех позиций перед выбором и соответствующих метаданных. Подтвердить, что хотя бы один активный байт позиции выбора у A и B различен. Иначе для этого префикса G0R получает NOT_EVALUABLE. G0R можно выполнять до G1.

**G1 — выполнение текстовой задачи.** Использовать немодифицированные истории. Сначала выбрать интерфейс на dev, затем один раз оценить замороженный вариант. PASS по правилу полных блоков из §2. На отдельных копиях выполнить три диагностических чтения: (а) воспроизвести $h$ до обратной связи по однозначному запросу на копирование, (б) назвать исправленное правило $p$ после обратной связи, (в) выбрать нужный конец при явно указанном правильном $p$ в новом контрольном эпизоде. Для первых двух указать правильность по каждой доступной комбинации, для третьего — по всем четырём сочетаниям концов. Они показывают, какой интерфейс у модели работает. Способность назвать промежуточный результат словами не является логическим условием решения основной задачи.

**G2 — проверка адресации на панели G1.** Снимок по-прежнему делается непосредственно после токена выбора в позиции $k$. Пусть $C_A=(U,a)$ и $C_B=(U,b)$, где $U$ — все активные позиции перед $k$ и общие метаданные. Тогда $P_B(C_A)=(U,b)=C_B$. Для детерминированного продолжения $F$ верно $F(P_B(C_A),e,x)=F(C_B,e,x)$ на любом суффиксе. Аналогично для обратного направления. Равенство с донором, технически достаточное для G0R, действительно делает прежний поведенческий G2 следствием G1 и точного воспроизведения на **тех же строках**.

После PASS G0, G0R и G1 повторить технические сравнения G0R на общей отложенной панели G1/G2. Отдельно проверить общую, совпадающую по длине историю X и формат её битовых ответов. При успешных побайтных проверках и прохождении порога формата вернуть REPLAY_OK. Протокол учитывает это как проверку адресации и воспроизводимости на панели. Независимого прироста свидетельств о локализации эта строка отчёта не даёт. Естественные смены решений A/B и полные блоки публикует G1. Частичный перенос представления проверяет G4.

**G3 — однократный сигнал в активациях.** Фиксировать на dev и заносить в манифест до теста нейтральный токен и позицию, слой, точку вмешательства до записи K/V, источник вектора и скаляр его масштаба. В dtype операции один раз сформировать конечный ненулевой $v$. Задать $v_0=+v$, $v_1=-v$ точной сменой знака уже представленного массива. Проверить форму, dtype, поэлементную противоположность и равенство ненулевых L2-норм, рассчитанных с одинаковым порядком в FP64. Для данного $e$ в обоих контекстах используется побайтно тот же тензор. После одного сложения хук выключается. Из-за округления фактическое приращение $\mathrm{round}(r+v_e)-r$ может зависеть от состояния $r$. Сохранять его норму отдельно для каждой ветви. Равенство норм поданных импульсов относится к каналу на входе.

Для PASS требуются G1 и G2/REPLAY_OK, формат §2 для всех обязательных числовых ответов и правило 9/12 полных блоков на отдельной панели G3 с данным импульсом. При отключённом импульсе обе ветви $e$ должны иметь идентичные входы и логиты при фиксированных $h,x$. Записать их точность и массу. Вердикт относится к выбору правильного бита по новым строкам.

**G4 — перенос состояния после закрытия исходных позиций.** После $h,e$ и до предъявления любой новой строки дать модели обработать один и тот же заранее зафиксированный нейтральный промежуток. $M_{he}$ — K/V только его заранее выбранных позиций и слоёв. Переносить их в общий свежий шаблон той же длины и с теми же позициями. Все остальные токены, активные K/V и метаданные между четырьмя историями идентичны. В этот шаблон не попадают исходный выбор, сообщение, логиты, результаты диагностики и прочие потомки исходной ветви. Для импульсного канала требуется G3, для текстового — G1 и REPLAY_OK. До открытия панели фиксируются канал, текст промежутка, его позиции и слои, шаблон получателя и способ получить $M_*$ из одной общей нейтральной истории.

- **Положительный контроль.** На той же панели с целой историей и тем же промежутком требуются формат §2 и 9/12 полных блоков. Если задача с целой историей провалена, прохождение G4 не устанавливается.
- **Целостность.** При подстановке общего $M_*$ подтвердить побайтное совпадение входов, кэшей и полных логитов для всех четырёх $h,e$ при фиксированном $x$. Проверить обратный перенос своего $M_{he}$ после чужого на том же производном снимке с возвратом исходных логитов. Нарушение даёт INVALID.
- **Поведение с памятью.** Блок засчитывается, когда для каждого из четырёх доноров $M_{he}$ выходы верны на всех четырёх сочетаниях концов. Тем самым доноры с одним $p$ дают одинаковые верные биты, а доноры с разными $p$ — противоположные верные биты на расходящихся концах. Требуются формат §2 и минимум 9/12 полных блоков.
- **Поведение после стирания.** На тех же обязательных строках отдельно подсчитать $C_M$ и $C_*$ — число верных ответов с перенесённым и с общим нейтральным состоянием при $L\ne R$. Знаменатель каждого равен $12\times2\times4=96$. Сосчитать полностью решённые блоки с $M_*$. Для PASS требуются валидный формат после стирания, $C_*\le48$, 0/12 полных блоков с $M_*$ и наблюдаемое парное падение $(C_M-C_*)/96\ge0.25$. Записать также числа исправлений и потерь при переходе от $M_*$ к $M$. При одинаковом входе, строгом бинарном выборе и сбалансированных метках $C_*=48$ следует из дизайна. При ничьих возможен меньший счёт. Результат с $M$ даёт содержательную сторону сравнения: 9 полных блоков гарантируют как минимум 72/96 на расходящихся концах.

PASS G4 утверждает функциональную достаточность перенесённого состояния при закрытом прямом доступе к исходным позициям. Многомерный $M$ может перенести оба бита для позднейшего вычисления XOR.

**G4-1 — отдельный строгий опыт с одним битом.** В этом варианте единственный канал от отправителя к получателю — ID одного токена. Первый вариант использует Base, текстовый сигнал и фиксированный prefix(8) исходного скорера. После токена выбора присоединить только строку `\nFeedback: correct` или `\nFeedback: wrong`, затем один и тот же запрос `\nRecord the corrected rule. Rule:`. Здесь и далее `\n` обозначает один перевод строки. Ни одна новая тестовая строка $x$ к этому моменту ещё не предъявлена. При фиксированном токенизаторе разрешёнными значениями носителя служат однотокеновые окончания « A» и « B». Замороженная модель делает один свободный greedy по полному словарю. При ничьей за первое место или третьем токене результат FAIL_FORMAT, повторной попытки нет. Для каждого префикса получаем четыре реализации в одном и том же порядке $00,01,10,11$ и фиксируем их до показа тестовых строк.

Общий чистый префикс получателя равен `Rule A selects the first bit. Rule B selects the last bit.\nRule:`. Внешний код дословно подаёт выбранный ID и вычисляет его K/V заново. Затем получателю предъявляется `\nBits: `, восемь битов $x$ через один пробел и `\nAnswer: ` с завершающим пробелом. Прямую композицию ID сверить с токенизацией целой строки в обеих ветвях. Ни K/V отправителя (включая K/V этого токена), ни скрытые активации, логиты, вероятности, время ответа, настройки семплирования или номер ветви получателю не передаются. Запросы отправителя и получателя, два ID, выбор чекпойнта и декодирование фиксируются до оценки этой версии. Для построения, выбора или настройки носителя запрещены подбор по меткам $p$, по $(h,e)$, по правильным ответам или любым их прокси и постфактум выбор удачных ветвей. Внешняя обучаемая проекция и квантизатор отсутствуют. Модель получает только публичное описание задачи, разрешённые демонстрации по фиксированному шаблону, собственный выбор и сигнал наблюдателя. Метки испытаний используются оценщиком по завершении фиксации выходов. Для контроля стирания передать во всех ветвях один и тот же заранее указанный ID « A».

Факторизация здесь имеет вид $(h,e)\longrightarrow m\in\{A,B\}\longrightarrow F(m,x)$. При нулевой ошибке на четырёх мирах для одного и того же будущего $x$ с $L\ne R$ разные $p$ требуют разных $m$. У двух $p$ и двух допустимых сообщений это вынуждает таблицу $0110$ либо $1001$ при A=0, B=1. Перестановка имён разрешена в математическом выводе. В рабочем получателе постфактум переставлять ID ради правильного ответа нельзя. Вывести таблицу сообщений по каждому фиксированному префиксу. Для утверждения ZERO_ERROR_ON_PANEL требуются все четыре валидных сообщения, 12/12 полных блоков, формат §2, технический контроль границы и контроль стирания. Требование 9/12 у многомерного G4 не заменяет этот строгий вердикт. Если обе версии оцениваются на одной панели G4, их параметры замораживаются совместно до первого открытия панели.

## 4. Статусы и выбор модели

Нарушение с наибольшим приоритетом определяет статус запущенного гейта. Проверять по порядку INVALID для нарушения технических условий или нечисловых данных, затем NOT_EVALUABLE при недоступных историях, затем FAIL_FORMAT при нарушении выходного формата, затем FAIL_DEV/FAIL_TEST при недостаточном поведенческом счёте. Зависимая невыполненная проверка получает NOT_RUN. Статусы первой серии сохранены в её отчёте. Новый технический G0R и перенос G4 на Base ещё предстоит выполнить.

Уравнения, подмены и гейты применимы к Base и Instruct. Чекпойнт с пройденным текстовым контролем нужен, чтобы интерпретировать срыв импульсного условия. Для установления свойства исходной Base эксперимент проводится на Base. Instruct может пройти тот же протокол как отдельная модель. Сопоставление при одном дословном префиксе проверяет смену чекпойнта. Применение собственного чат-шаблона меняет ещё и интерфейс и должно помечаться отдельным условием.
